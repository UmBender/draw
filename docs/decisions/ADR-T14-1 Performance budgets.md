# ADR-T14-1 Performance budgets

## Context

[[T14 Performance and release validation]] has to prove the app stays fast
on the target laptop (i5-8250U, Intel UHD 620, Wayland). The hot paths that
scale with the document are hit-testing (select, eraser), the culling pass
of every redraw, finishing a stroke, and, since [[ADR-T17-1 Snapping order
and tolerances]] and [[ADR-T20-1 Outline snapping]], snapping: every pointer
move of a snapped drag rebuilds the targets from the whole document and
checks every outline.

A first measurement on the target with 10 000 mixed shapes (strokes, lines,
arrows, filled and numbered boxes, 8 × 8 grids with indices and filled
cells), release build, median of 101 runs:

| Operation | Median |
|-----------|--------|
| Hit-test miss (whole document scanned) | ≈ 0.35 ms |
| Eraser outline scan | ≈ 0.3 ms |
| Culling pass | ≈ 0.25 ms |
| Stroke finish, 1 000 points (High) | ≈ 13 µs |
| RDP on 1 000 raw points | ≈ 60 µs |
| Snapped box drag, one move | ≈ 0.9–1.1 ms |

## Decision

- Performance is checked by `#[ignore]`d tests in `tests/perf.rs`, run in
  release mode with one test thread:
  `cargo test --release --test perf -- --ignored --nocapture --test-threads=1`.
  Debug builds skip the checks. Each test compares the **median** of 101
  timed runs (after 5 warm-up runs) with its budget.
- Benchmark document: 10 000 shapes, an even mix of the six shape kinds
  above, scattered over a 20 000 × 20 000 world, generated by a fixed-seed
  xorshift so every run measures the same data.
- Budgets:
  - hit-test, eraser scan, culling pass, stroke finish and RDP on 1 000
    points: **< 1 ms** each (the T14 spec);
  - one snapped pointer move (target rebuild + `snap_drag`): **< 4 ms**, a
    quarter of a 60 Hz frame. Snapping was not in the original 1 ms list and
    sits right at it, so a 1 ms budget would fail at random.

## Alternatives considered

- **1 ms for snapping too** — fails about half the runs today; making it
  pass needs cached targets or a spatial filter on outlines in
  `core::snap`, a new feature outside T14 (and its files).
- **A benchmark harness (criterion)** — better statistics, but a new
  dependency ([[ADR-0014 Minimal dependencies and no unsafe]]); a median
  over `Instant` is enough for budgets this far apart from the measurements.
- **Mean instead of median** — one scheduler hiccup would move it.

## Consequences

- Regressions in the hot paths show up as a failing ignored test, run before
  a release.
- Snapping is the slowest per-event path; with very large documents it is
  the first candidate for optimisation (cache `Targets` for a drag, skip
  outlines whose box is beyond the tolerance).
- Timings depend on the machine; budgets are for the target laptop.

## Rollback plan

Budgets are constants in `tests/perf.rs`; changing one is a new ADR amending
this one.
